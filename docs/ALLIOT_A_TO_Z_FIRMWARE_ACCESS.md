## 2. First operation: change boot state, not the complete OS

Alliot credits earlier Chinese community research for discovering that Action 5 Pro uses Snapdragon 8 Gen 2-class Qualcomm hardware and can enter **9008/EDL**; he did not claim to invent that hardware access. His article specifies:

1. **Hardware EDL access** using a Qualcomm second-generation EDL engineering USB cable. With power off and battery temporarily removed for cable insertion, his camera enumerated as **`05c6:9008` (`QUSB_BULK`)**, a mode separate from normal ADB and Fastboot. Battery was reinstalled to avoid interruption during storage operations. `AUTHOR-HARDWARE`.
2. **Qualcomm EDL tool:** [`bkerler/edl`](https://github.com/bkerler/edl), author-pinned commit **`2f8e89a848afaaef68997fcbcb5b178d958d497b`**, with `libusb` and Python in an isolated host virtual environment. This runs **on the host**, not on the camera. The **RedMagic-named 8 Gen 2 devprg** from the verified ZIP was used as its Firehose programmer; author explicitly states he tested that combination on Action 5 Pro. `AUTHOR-HARDWARE + OUR-OFFLINE`.
3. **Read-only geometry first:** EDL `printgpt` to inventory the camera's actual UFS logical units, GPT, `devinfo`, active `abl_a` / `abl_b` slot, sector sizes and partition boundaries. In his specific camera, both target partitions were on **LUN 4**, slot **A** was active. He explicitly forbids copying someone else's sector offsets or adapting steps blindly to slot B. `AUTHOR-HARDWARE`.
4. **Backup before writes:** author performed EDL partition reads (`rl` / `rs`) of key partitions, including **the device's own `devinfo`, `abl_a`, `abl_b`**, and separately `userdata`; kept SHA-256 manifests and a second external backup. He warns not to flash another owner's `userdata.img` because it contains device identities, radio secrets, settings and calibration. `AUTHOR-HARDWARE`.
5. **First persistent change — `devinfo`:** after verifying a **4096-byte** image with `ANDROID-BOOT!` magic, he prepared **a modified copy of his own file**, changing just two 0→1 flags: at **offset `0x10`, `is_unlocked`; offset `0x18`, `is_unlock_critical`**. He verified exactly two byte differences, then wrote only that partition's single sector via Firehose, immediately reread and byte-compared it. **Do not use those offsets unless the original structure is independently validated on the exact device.** `AUTHOR-HARDWARE`.
6. **Intermediate boot test:** he reset the device **before touching ABL**; it still booted normal production firmware, **without ADB**. This separated the bootloader-unlock flag result from the engineering-debug result. `AUTHOR-HARDWARE`.
7. **Second persistent change — active ABL:** reentered 9008, **reconfirmed GPT, active slot A, original ABL backup and exact factory-image hash**, then replaced only **active `abl_a`** with the 1 MiB **`abl-factory.img`** from the ZIP. He immediately read the partition back and compared all bytes; **did not modify `abl_b`, GPT or `userdata`**. `AUTHOR-HARDWARE + OUR-OFFLINE`.
8. **Engineering boot:** after reset, the factory ABL passed kernel boot parameters **`mp_state=engineering`** and **`androidboot.secure_debug=1`**. The stock DJI filesystem already had `/sbin/adbd`, `/sbin/launch_adbd`, `/lib/systemd/system/adbd.service` and `/sbin/usb/compositions/*`; the ADB daemon service was already **enabled**, but production ABL had not exposed the needed debug USB mode. Engineering boot **activated those existing components**. `AUTHOR-HARDWARE`.
9. **Read-only verification after boot:** normal USB showed `product:qcs8550_ac204`; `adb shell id` returned **`uid=0(root)`**; systemd reported `adbd.service` **enabled and active**. The author separately entered Fastboot and verified **`unlocked: yes`**, `current-slot: a`, and `product: kalama`. He verified ADB returned after reboot. `AUTHOR-HARDWARE`.

**Crucial distinction:** the released ZIP has **two donor boot-related binaries** only; the `devinfo-minimal-unlocked.bin` patch and all per-camera backups are **not** in it and must derive from the individual camera. The exact operational write commands and offsets in the blog refer **only to his physical device**, not to a validated procedure for ours. No EDL write operation was made by this project.

### Source-confirmed rollback plan, not yet rehearsed by us

The author documents returning through 9008, reconfirming the device's GPT and original saved hashes, restoring **the device's own original ABL first, then the original `devinfo`**, checking readback, and rebooting. This depends on persistent EDL access and a trustworthy, intact personal backup; **it is not a guaranteed unbrick service**. He lists stop conditions: Firehose instability, different model/firmware/GPT/active slot, unexpected `devinfo` structure/flags, mismatched factory ABL, no redundant backups, readback errors, power/temperature trouble, or instructions to overwrite GPT/XBL/calibration/identity partitions. OTA could replace ABL and remove root ADB without relocking `devinfo`.

## 3. Second operation: install additional software next to DJI firmware

Alliot then authored **Action Control**, a separate open-source project, after root ADB was already working:

1. **Code:** Go backend + React/Vite web frontend, built into an **ARM64 Linux application bundle**; the GUI extension is compiled separately as a native shared object. The ZIP studied above is **not** this application installer; he builds a different release from GitHub source.
2. **Transfer/install over root ADB:** the installer checks `id -u=0`, product/architecture, package SHA-256 and explicit device identity, stages files, then deploys the app under **`/blackbox/upgrade/action-control`**. The install/update process records rollback/ownership metadata; there is a separate uninstaller for these addon changes.
3. **Persistence:** installs **`action-control.service` and `action-control-network.service`** managed by **systemd**, with boot integration via `/etc/init.post_boot.sh` because of the camera's overlay filesystem/service load order. That means the extra process automatically starts on the camera's **existing Linux**; there is **no Debian install**, no Android APK and no wholesale ROM replacement.
4. **Web UI:** the Go service listens by default on **port 8080**. On DJI's native hotspot the author's address is **`http://192.168.2.1:8080`**, or it can be reached locally by **ADB USB port forwarding**. React runs in a **browser on phone/computer**; the camera runs the server.
5. **Backend features:** device status (battery/temperature/CPU/storage), SD/internal file browsing and upload/download, media index `AC004.db` metadata, process/service management, root system operations, hotspots, recording start/stop, still photo and proven Photo/Video profiles.
6. **Native capture reuse:** Go launches camera-side **Python 3/ctypes** in an isolated subprocess. It fingerprint-checks DJI's proprietary **`/usr/lib/libdcam_camera_service_client.so`** and corresponding server library, then talks through the original local **Binder camera service**. On his device he verified real `record_state` **3→1→3** during record/stop and a saved MP4. DJI still does the actual sensor, encoding, storage and thermal management. The standalone mode that stops DJI camera/screen/Mimo services exists as a riskier optional branch; default is coexistence.
7. **Preview caveat:** live Web preview is a repackaging of an **existing DJI Mimo** preview stream (H.264→MPEG-TS) without re-encoding. Mimo still needs to maintain its preview stream. This feature **does not** prove a totally independent on-camera RTSP/live feed.
8. **Real on-camera menu addition:** with collaborator **Astra** and reverse engineering of DJI GUI binary structure, Alliot compiled **`libaction_control_gui.so`** to wrap the existing **`gui_image_loader_create`** plugin entry. On a firmware-matched **rear GUI**, it appends an `Action Control` row to native **System Settings**, opening an Embedded Wizard panel with a hotspot toggle and two QR codes. It runs UI callbacks on `ew_gui_thread` and delegates the original image-loader behavior rather than replacing the GUI executable.
9. **Persistent GUI integration:** installer rewrites the matching plugin entry in `/etc/disp0_plugins_config.json` to point to `/blackbox/upgrade/action-control/bin/libaction_control_gui.so`, adds `ac_mode=menu;ac_state=/run/action-control-ui-persist;`, and restarts `gui.service` when necessary. It backs up the original config at `.restore/gui-plugin.json`; removal reverts addon GUI config. Exact **`dji_gui_on_disp0`** SHA-256 is checked, otherwise the extension is disabled. GUI freeze was once observed during earlier tests; an independent watchdog/rollback trial was built.
10. **Limits/security:** default HTTP root admin interface **has neither authentication nor TLS**, and can control processes/reboots; do not expose it to untrusted networks. Addon uninstall restores managed app/network/GUI changes, **but does not re-lock the bootloader, disable engineering root ADB or exit Factory Mode**.

## 4. What has *not* been achieved for our 10-hour native Timer Shooting

- **No DJI source code released:** Alliot accesses **compiled ELF vendor libraries** and reverse-engineered private entry points; he did not open-source the camera's source tree.
- **No Debian-style OS replacement:** his process coexists with vendor services; default camera recording remains handled by DJI.
- **No verified Timer Shooting task setter:** existing native methods cover Photo, Video, record/capture, read-only settings; no confirmed schedule duration setter, 5 h UI validator or mode ID for Timelapse.
- **No tested 10h duration, RTC wake, or repeat schedule:** an added GUI item can display a 10 h choice, but the actual native service must accept, persist, wake, shoot and stop for 36,000 s. Separate [target design](ACTION5_TIMER10H_FIRMWARE_TARGET.md).
- **No owner-camera root validation yet:** Alliot's `10.00.16.13` hardware results do not qualify our camera until we verify its exact firmware, product, hashes, boot state and recovery access.

**Best technical leverage:** reuse his proven **fingerprint-gated native GUI plugin model** and Binder service reverse engineering *after* an exact Timer Shooting backend getter/setter is identified. The root/EDL approach is a one-time **development/installation path**; the eventual 10h task must function on the camera unattended without external BLE/Pi/ESP32.
